# 项目说明

比赛模型提交服务。参赛队伍用浏览器把「模型文件夹 + Docker 镜像」上传到
`/data/submissions/<队伍名>/`；服务端实算每个文件的 SHA256 并给出
`sha256sum -c` 可用格式的校验码，参赛者可本地核对。

## 组成

- **服务端**：`.service/app.py`（Flask app，单文件；生产由 waitress-serve 加载，
  端口 8080，见 `决策记录.md` 2026-10-15）
- **前端**：`.service/static/index.html`（单页，无构建步骤；含纯 JS 流式 SHA256、
  文件并行上传 + 速度/预计剩余时间显示、文件篮式选择入口）
- **公网入口**（三条线路）：
  1. **直连（主）**：`http://<公网IP>/` —— 公网 80 端口 → 云 NAT →
     SSH 入口机 <入口机IP>（别名 `<入口机SSH别名>`）上的 `submissions-port80.service`
     （纯 TCP 转发到本机 8080）。公网实测 22MB/s，无需任何安全组/控制台改动
     （见 `决策记录.md` 2026-10-15）
  2. cloudflared 快速隧道（备用，地址随重启变化，见 `参赛提交说明.md`；
     有 100s 源站超时，慢线路 524 无害，断点自动续传）
  3. SSH 反向隧道 `<公网IP>:8080`（休眠：云 NAT 当前未转发 8080 端口，
     不可达；若日后放行 8080 则自动可用）
- **测试**：`tests/test_e2e.py`（全流程 E2E）、`tests/test_resume_524.py`
  （断连/续传/并发回归）、`tests/test_js_sha.py`（前端 SHA256 与 openssl 对拍）

## 提交流程

1. 登录（提交口令）→ 填队伍名 → `POST /api/session` 建会话（队目录已存在则拒绝，防覆盖）
2. 每个文件：浏览器「文件篮」选文件（PC 选文件夹 / 手机多次「添加文件」累加，
   见 `决策记录.md` 2026-10-15）→ ≤1GB 文件浏览器预算 SHA256
   （>1GB 免预哈希，begin 传空 sha）→ `/api/file/begin`（断点续传返回 offset）→
   256KB–16MB 自适应分片 `POST /api/file/chunk`（头带 `X-Sid`、
   `X-Relpath`=encodeURIComponent(relpath)、`X-Offset`=客户端预期的 part 当前大小，
   不一致回 409 + 实际 offset 重同步）→ `/api/file/finalize`（服务端重算 SHA256
   比对，空 sha 文件以服务端实算值为准，从 `.parts/` 转正）
3. 镜像（可选）：上传 `docker save` 出的 tar 文件（2026-10-14 起移除服务器侧拉取方式，
   见 `决策记录.md`）
4. `POST /api/finalize-session` → 生成 `SHA256SUMS` + `SUBMIT_INFO.json`，清理 `.parts/`

**报错上报**：前端在最终失败（文件重试耗尽 / 完成提交失败）时调
`POST /api/client-error` 把浏览器端错误信息上报，存入会话（每会话留 50 条）；
管理页状态列显示报错条数，详情里可按时间查看（`/api/admin/teams` 返回 `errors` 字段）。

## 部署

四个 systemd unit（备份在 `systemd-units/`，实跑文件在 /etc/systemd/system/）：

| unit | 部署位置 | 作用 |
|---|---|---|
| `submissions-web.service` | 本机 | 跑 app.py（waitress），日志 → `logs/service.log` |
| `submissions-cloudflare.service` | 本机 | cloudflared 快速隧道（备用线路），日志 → `logs/cloudflared.log` |
| `submissions-tunnel.service` | 本机 | SSH 反代隧道（休眠，见上） |
| `submissions-port80.service` | **入口机** | 直连转发 `:80 → <数据机IP>:8080`；入口机重装时按 unit 头注释重装 |

改了 `app.py` 后执行 `systemctl restart submissions-web`（`index.html` 是静态读取，改后无需重启）。

## 状态与数据

- 会话状态：`.service/state/sessions.json`（服务内存 + 该文件双份，每秒/关键节点落盘）。
  服务重启时：`pulling` 状态的旧镜像任务（2026-10-14 前方式残留）标记为
  `interrupted`；队目录已不存在的活跃会话由 `load_sessions()` 自动清理。
- **残留会话手工清理**（兜底，如服务运行中需要清理时）：
  ```bash
  systemctl stop submissions-web
  /data/submissions/.service/venv/bin/python - <<'EOF'
  import json, pathlib
  p = pathlib.Path("/data/submissions/.service/state/sessions.json")
  s = json.loads(p.read_text())
  s = {k: v for k, v in s.items() if pathlib.Path(f"/data/submissions/{v['team']}").exists()}
  p.write_text(json.dumps(s, ensure_ascii=False))
  print("kept", len(s))
  EOF
  systemctl start submissions-web
  ```
- 队伍数据目录（含 `.parts/`）是运行时产物，不入 git（见根目录 .gitignore）。

## 容量与限额

单文件 ≤100GB，单队 ≤200GB，单次请求 ≤16MB，磁盘剩余 <5GB 停止接收。
限流 3600 req/min/真实客户端 IP（CF 线路按 CF-Connecting-IP；直连流量全部
归于入口机 IP（<入口机IP>），共享一桶，量级足够，见 `.agents/context.md`）。
