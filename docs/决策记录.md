# 决策记录（know why）

## 2026-10-14 修复：中文文件名上传报 fetch 错

**现象**：参赛者上传含中文目录/文件名的模型时报
`Failed to execute 'fetch' on 'Window': Failed to read the 'headers' property from
'RequestInit': String contains non ISO-8859-1 code point`。
服务器会话状态佐证：队伍 A 的 `即梦/...` 四个文件全部停在 `received: 0`。

**根因**：分片上传用 `X-Relpath` **请求头**携带相对路径，浏览器 fetch 规范要求
header 值只能是 ISO-8859-1 单字节字符，中文（多字节 UTF-8）直接触发异常，
请求根本发不出去。此前 E2E 测试全部用 ASCII 路径，未覆盖到。

**方案**（备选与否决理由）：
- ✅ 采用：前端 `encodeURIComponent(relpath)`，服务端 `unquote()` 还原。
  理由：改动最小（前端一行 + 服务端一行），符合"二进制/特殊字符走 body，头只放安全字符"的
  HTTP 惯例；服务端对不含 `%` 的旧式裸 ASCII 头向后兼容（unquote 无副作用）。
- ❌ 把 relpath 改放进 body：chunk 接口是原始字节流 body（8MB 分片直写磁盘），
  没有 JSON body 位置；另加 JSON side-channel 会引入并发/乱序问题，收益为负。
- ❌ 只改前端 `escape()`/`unescape()`：已废弃 API，语义与 encodeURIComponent 有差异。

**涉及文件**：`.service/app.py`（file_chunk 的 unquote）、`.service/static/index.html`
（chunk fetch 头）、`tests/test_e2e.py`（新增"即梦/extract_prompts.jsonl"中文路径回归用例，
全部 X-Relpath 改为百分号编码发送）。

## 2026-10-14 新增：管理页可见参赛者端报错

**动机**：2026-10-14 的中文路径 fetch 报错只有参赛者自己看得见，组织者在管理页
只能看到文件卡在 0 字节，无法知道"为什么"。需要一个通道把浏览器端失败原因
（fetch 异常、HTTP 错误等）传回服务端。

**方案**（备选与否决理由）：
- ✅ 采用：前端在**最终失败**时（文件重试 2 次仍失败 / 镜像拉取启动失败 / 完成提交失败）
  调 `POST /api/client-error` 上报 `{sid, relpath, message}`；服务端清洗（去控制字符、
  截断 300 字符）后存入会话 `errors`（每会话最多留 50 条，随 sessions.json 持久化），
  `GET /api/admin/teams` 返回每队最新 20 条；管理页状态列显示「⚠ N 条客户端报错」，
  点「校验码」在详情里看完整列表（带时间戳和文件名）。
- ❌ 管理页直接 tail 服务端日志：只能看到服务端视角，看不到浏览器端异常（本次故障
  正是浏览器端报错），且日志无队伍归属结构。
- ❌ 每条失败都实时上报（含自动重试前的失败）：噪声大，自动重试成功的文件也会留下
  误导性的报错记录，故只在重试耗尽后上报一次。

**涉及文件**：`.service/app.py`（`/api/client-error` + admin teams 返回 errors）、
`.service/static/index.html`（`reportError()` + 三处失败路径 + 管理页展示）、
`tests/test_e2e.py`（5 个新用例：上报/空内容/坏会话/角色隔离/管理页可见）。

## 2026-10-15 修复：慢线路 524 导致大文件上传死循环

**故障**：队伍 A（某模型厂商数据集）上传 60MB/759MB 文件反复失败。参赛者走 Cloudflare
快速隧道（出口洛杉矶），国内实际速率约 60KB/s，前端 8MB 分片单请求超过
Cloudflare 100s 源站硬超时 → `HTTP 524`。更严重的是服务端 chunk 处理：
`received` 计数器取自会话状态而非磁盘实际大小、同一文件无并发锁、盲追加写
`.part`。524 断连后部分数据已落盘，客户端重试时 offset 与计数器错位，重复
数据累积 → 超过声明大小 → 400「数据超出声明大小」→ 整个文件推倒重传，
形成死循环（日志中 11:40-11:52 连续 11 次 chunk 400）。

**修复**：
- `app.py`：
  - 每 `(sid, rel)` 一把上传锁（`file_lock`），begin/chunk/finalize 的 part
    操作全部纳入；锁序约定 file_lock 在外、全局 `_lock` 在内。
  - chunk 新增 `X-Offset` 请求头 = 客户端预期的 part 当前大小；不一致时
    返回 409 + 实际 offset，客户端重新同步后续传（已落盘内容仍是有效文件
    前缀，不丢弃）。旧客户端不带此头则跳过校验，保持兼容。
  - chunk 以磁盘实际大小（`actual`）为计数器起点，不再信会话里的旧值。
  - 请求体读取中途异常（上游断连）时保留已写数据、状态落盘后正常返回。
  - `load_sessions()` 启动时清理队目录已不存在的活跃会话（僵尸会话，
    如管理员删队后遗留；清理方法原本就写在 项目说明.md）。
- `index.html`：
  - 分片 8MB → 4MB：40KB/s 也能在 100s 内传完一个分片，524 大幅减少。
  - SHA256 按 `rel+size` 缓存，自动重试不再重算（759MB 重算要几分钟）。
  - chunk 409 时按服务端返回的实际 offset 重新同步继续，不触发整文件重试。
  - chunk 400（数据超限）或 finalize SHA 校验失败时打 `restartNeeded` 标记，
    下次 begin 带 `X-Restart: 1` 从头重传该文件（服务端配合：part 超过声明
    大小时 begin 自动删除重传）。
- `参赛提交说明.md`：提示大文件建议用直连地址（无 100s 限制），两地址进度
  共享可混用。

**遗留说明**：Cloudflare 快速隧道的 100s 源站超时是平台硬限制，服务端无法
绕过；慢线路下仍可能偶发 524，但现在 524 无害（断点续传自动恢复，数据不
损坏、不重传整文件）。彻底避免只能换线路（直连/正式域名+更高超时的代理）。

## 2026-10-15 加固：waitress 生产化 + 大文件/并发支持

**背景**：正式比赛前最后加固。后续参赛者单压缩包可达几十 GB、多队伍并发
上传，磁盘将扩至 1T。同时排查"直连地址无法访问"。

**直连诊断结论**：SSH 反代隧道（`ssh -R 0.0.0.0:8080:127.0.0.1:8080`）本机、
远端监听、GatewayPorts、远端防火墙、远端 curl 全部验证通过，**唯一堵点是
<公网IP> 的云安全组未放行入站 TCP 8080**——需在云厂商控制台加规则，
服务端无法代劳。规则加上后直连即可用，`参赛提交说明.md` 措辞已改为
"目前尚未开放"。

**改动**：
- **waitress 3.0.2 替换 Flask 开发服务器**（`docs/systemd-units/submissions-web.service`
  同步）：`waitress-serve --listen=0.0.0.0:8080 --threads=64 --channel-timeout=600`。
  开发服务器（单进程、线程池小、官方声明非生产）不再承担正式流量，仅留作
  应急回退（`main()` 保留）。
- **关键发现（waitress 3.x 语义）**：请求体收齐（parser `completed`）才创建
  WSGI task 调用 app——body 先缓冲（内存 512KB 上限，超出 spill 临时文件）。
  因此**请求体中途断连时 handler 根本不会被调用**：chunk 是全有或全无——
  收齐的 chunk 完整落盘，断连的 chunk 一个字节都不写（开发服务器则是保留
  已收前缀）。两种语义下 `X-Offset`/409 重同步机制都成立（还多覆盖一种
  "服务端已收完但 200 响应丢失"的错位场景），断点续传协议不变；代价只是
  断连的分片（≤16MB）重试时整片重传。app.py 的 `chunk 写入中断` 异常分支
  在 waitress 下不会触发，保留作开发服务器回退时的兜底。
- **限流按真实客户端 IP**（`client_ip()`：CF-Connecting-IP → X-Forwarded-For
  首段 → remote_addr）：经隧道后 remote_addr 全是 127.0.0.1，原实现所有
  队伍共享一个限流桶，并发上传会互相挤掉。`MAX_REQ_PER_MIN` 600→3600
  （大文件分片上传轻松 >10 req/s）。
- **上限提高**：单文件 50→100GB，单队总量 60→200GB（磁盘扩容在即）。
- **大文件免浏览器预哈希**：>1GB 的文件前端 begin 传 `sha256=""`（759MB
  文件浏览器端哈希要几分钟且阻塞页面）；服务端 begin 接受空 sha，
  已 done 的空 sha 文件直接返回 done+服务端实算值，finalize 跳过比对、
  一律以服务端实算值返回给参赛者核对。
- **前端分片自适应**：固定 4MB 改为 1–16MB 自适应（`CH_MIN`/`CH_MAX`，
  初值 4MB，每片按实测速率调整目标"25s 传完一片"），524/504/502/网络
  异常时减半。慢线路自动用更小分片降低 524 概率，快线路自动放大提吞吐。

**测试**：`test_e2e.py` 46/46；`test_resume_524.py` 32/32——其中断连用例
的断言从"已传部分保留在 .part"改为"**磁盘 .part / begin offset / 会话
received 三者一致**"（两种服务器语义都通过）；修复了测试里 Set-Cookie
未截属性的隐患；新增 70GB begin、双队伍并发上传用例。

**遗留**：云厂商控制台为 <公网IP> 加入站 TCP 8080 规则后，直连
地址可用，届时更新 `参赛提交说明.md`。

## 2026-10-15 直连打通：公网 80 端口 → 入口机 TCP 转发（零控制台改动）

**背景**：用户无云厂商控制台权限（安全组加 8080、TOS 开桶都做不到）；
Cloudflare 线路国内 ~60KB/s，无法支撑几十 GB 提交。之前"直连只差安全组
8080 规则"的结论作废——找到了不需要控制台的路。

**诊断过程**（全部实测）：
- 外部多节点探测 <公网IP> 入站端口：22 通；80 回 **Connection refused**
  （包到达机器、无人监听才回 RST，不是安全组 DROP）；8080/3000 全部超时
  （被丢弃）——所以之前 8080 直连不通。
- 数据机（本服务所在机）内网 IP <数据机IP>，公网 IP 在云 NAT 层；
  `ssh <入口机SSH别名>`（=<公网IP>:22）落在 **SSH 入口机 <入口机IP>**
  （另一台机器，VLLM GPU 节点）。
- 两台机器各在 80 端口放标记文件，用户浏览器实测：外部流量
  <公网IP>:80 **落在入口机**（NAT 的 80 DNAT 指向入口机）。
- 公网回环实测（数据机 → <公网IP>:80 → 入口机转发 → 数据机 8080）：
  **稳定 22~24 MB/s（≈200Mbps）**，服务端链路不是瓶颈；参赛者浏览器
  慢于该值即为其本地上行/路由上限。

**实现**：
- 入口机 .0.7 新增纯 TCP 转发器（systemd `submissions-port80.service`，
  Restart=always 已 enable）：`0.0.0.0:80 → <数据机IP>:8080`，
  每连接一线程、双向 1MB 管道、不解析 HTTP。脚本与 unit 备份在
  `docs/systemd-units/relay-port80.py` 和 `submissions-port80.service`
  （**部署在 .0.7 上，不在本机**；.0.7 重装需按 unit 头注释重装）。
- 提交服务仍监听 8080；cloudflared 隧道（→127.0.0.1:8080）保留作备用线路。
- 参赛者入口改为 **http://<公网IP>/**（80 端口，URL 不带端口号）。
  IP 直连、无域名，不需要 ICP 备案。
- 已验证：入口机本机 curl 200、用户浏览器页面+上传均正常（某队 1.4GB
  APK 经直连提交成功，SHA256 核对一致）。

**注意**：
- 直连流量 remote_addr 全是 <入口机IP>（转发器不传 XFF），限流桶被所有
  直连用户共享（3600 req/min，对十几队分片上传余量足够，非实际瓶颈）。
- 否决过的方案：TOS/OSS 直传（无账号权限）、mega.nz 转存（本机不可达
  mega）、另购国内中转机（现有 NAT 80 已满足，不必花钱）。

## 2026-10-15 前端：const 报错修复 + 模型文件上传入口统一

- **修复 `Assignment to constant variable`**：`fileMeta` 声明为 `const`
  但 `beginUploadFlow()` 中需重置，点「开始提交」即抛 TypeError、上传流程
  中断。改 `let`；全文件排查 const/let，此为唯一一处。
- **上传入口统一（移动端适配）**：手机浏览器（iOS/微信）不支持
  `webkitdirectory`，控件静默退化为文件选择器，导致 PC 选文件夹、手机
  只能一个个选文件，体验不一致。方案=**文件篮（basket）模型**：
  `basket` 数组为唯一事实源；「选择模型文件夹」（PC，webkitdirectory）与
  「添加文件」（手机，multiple、**可多次点击累加**）都汇入
  `addFiles()`（按 rel+size 去重）；已选列表可见、可单个移除；
  `collectFiles()` 只读 basket。手机选择无文件夹前缀（relpath=basename，
  落在队目录根下），服务端本就支持两种路径形态，SUBMIT_INFO 记录实际
  路径。「手机选文件夹」是浏览器级限制（iOS 完全无文件夹选择器），
  无法实现，只能统一为"同一提交流程 + 双入口"。
